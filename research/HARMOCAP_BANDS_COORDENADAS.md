# HarMoCAP: el modo de bandas cambia el significado de las muñecas OSC

**Auditoría de código público y fixture aislado, 3 de octubre de 2026.** Se comparó el `main` de [HarMoCAP `25fda8d`](https://github.com/AlterMundi/HarMoCAP/tree/25fda8d74c663a573aab6bc8f540c2c46ef250b9) con el commit `bdeebbf5` antes auditado. Se ejecutó el método `HarmocapPipeline.step` de ese commit con objetos sintéticos, sin inicializar cámara, backend, socket, servicio o audio. El cambio importa para usar pose como dato científico de rope flow y para entregar a Weaver valores con unidades inequívocas.

El [contrato OSC 1.4](https://github.com/AlterMundi/HarMoCAP/blob/25fda8d74c663a573aab6bc8f540c2c46ef250b9/schemas/osc_contract.v1.json) define cada `keypoints` como `(x_iso,y_iso,conf)`, con `x_iso=x_px/frame_h`, origen arriba a la izquierda y sentido hacia la derecha. En el [CLI actual](https://github.com/AlterMundi/HarMoCAP/blob/25fda8d74c663a573aab6bc8f540c2c46ef250b9/scripts/run_realtime.py), `--pads-mode bands` asigna `_bands_mode=True` al pipeline. En ese modo, el [pipeline](https://github.com/AlterMundi/HarMoCAP/blob/25fda8d74c663a573aab6bc8f540c2c46ef250b9/src/harmocap/pipeline.py) conserva una copia local `raw_keypoints` para el dibujo, pero reemplaza `x` de muñecas 9 y 10 por `clip(|x_muñeca−x_nariz|/band_span,0,1)` antes de construir `PersonState.keypoints` **y** `keypoints_blob` OSC. `band_span` se deriva del ancho de hombros y puede cambiar durante la toma. Las features se extraen **antes** de ese reemplazo, de modo que el mismo bundle puede contener features calculadas de coordenadas originales junto a muñecas OSC transformadas. La copia `raw_keypoints` no viaja en ese blob.

Un [fixture reproducible sin dependencias de cámara](verificar_harmocap_bands_osc.py) muestra la pérdida con el `step` y el codec **reales** del commit fijado: con nariz `x=0,6`, hombros `x=0,5` y `0,7` (`band_span=0,5`) y muñecas `x=0,2` y `1,0`, el blob OSC de `grid` devuelve `(0,200000003; 1,0)`, mientras el de `bands` devuelve `(0,800000012; 0,800000012)` por precisión float32. La copia local `raw_keypoints` conserva `(0,2; 1,0)` en ambos modos. El receptor del blob no puede reconstruir cuál muñeca estaba a cada lado de la nariz. La transformación sirve como control de **distancia simétrica para bandas**, pero ya no satisface el significado de posición horizontal del contrato para esas articulaciones; una trayectoria, lateralidad, dirección, `Q` proyectado o fase calculados desde ese blob podrían quedar alterados. El fixture **no** comprueba captura óptica, suavizado real, UDP, la escritura JSONL ni el receptor Weaver.

Reproducción sin instalar dependencias del pipeline: clonar HarMoCAP en un directorio temporal, fijar el commit `25fda8d74c663a573aab6bc8f540c2c46ef250b9` y ejecutar `python3 research/verificar_harmocap_bands_osc.py /ruta/a/HarMoCAP` desde este repositorio. El script exige `HEAD` exacto y checkout limpio; extrae sólo `step` del código fuente y carga el codec OSC de biblioteca estándar. No se deben interpretar sus valores artificiales como una medición de las cámaras de Saira.

El [`config_hash` del pipeline](https://github.com/AlterMundi/HarMoCAP/blob/25fda8d74c663a573aab6bc8f540c2c46ef250b9/src/harmocap/pipeline.py) incorpora modelo, suavizado, identidad, features, reacquisición y `mode`, pero `_bands_mode` se fija **después** desde el CLI y no entra en ese hash. El manifiesto/`contract_id` tampoco declara la excepción de bandas. Por inspección del código, dos sesiones con iguales configuraciones salvo `--pads-mode grid`/`bands` pueden compartir identificadores de contrato/configuración y emitir distintas semánticas para `x` de muñeca. No afirmamos que un receptor específico ya haya producido un resultado incorrecto: eso requeriría una prueba de integración.

**Decisión para el programa:** archivar video original y metadatos de CLI; para cualquier extracción científica desde OSC, usar `--pads-mode grid` o `none` hasta verificar con un fixture que `keypoints_blob` conserva la coordenada del contrato. Separar en una futura corrección del productor `keypoints_iso` y `band_control` como canales distintos, con identidad/versión del modo y tests de ida y vuelta. Si sólo existe un archivo capturado en modo `bands`, sus muñecas OSC se consideran **no válidas como posición de imagen**; se recuperan desde original/pose anterior a la transformación si existe y se valida, no invirtiendo el valor absoluto. Esta nota no modifica HarMoCAP ni sustituye una Issue/PR de implementación en su repositorio.
