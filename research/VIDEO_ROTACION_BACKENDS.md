# Un MP4 rotado no define por sí solo el mismo marco para pose y soga

**Cotejo sintético offline, 3 de octubre de 2026**, para la [issue de investigación #9](https://github.com/SairaAsua/movimiento-armonico-investigacion/issues/9). [Script reproducible](video_rotacion_pts_sintetico.py). Se crearon cuatro cuadros RGB asimétricos de `64×32` a 10 fps, codificados sin pérdida, y una copia **del mismo stream de video** con matriz de visualización de `90°` agregada mediante FFmpeg. No son datos humanos ni una prueba de cámara.

Con HarMoCAP PR [#4, commit `e0bdafc`](https://github.com/Mar-IA-no/HarMoCAP/pull/4), `probe_video_timeline()` aceptó ambas versiones y registró los mismos PTS enteros `0,1024,2048,3072` con base `1/10240` s; los hashes de archivo fueron diferentes, como corresponde a medios distintos. El `VideoCapture` de OpenCV 5.0.0, en su modo automático predeterminado, devolvió los cuatro cuadros de la copia rotada en `32×64` píxeles de imagen (`shape_yx=(64,32)`), idénticos **píxel por píxel** a FFmpeg con autorrotación. Al desactivar `CAP_PROP_ORIENTATION_AUTO`, OpenCV devolvió `64×32`, idéntico a FFmpeg `-noautorotate` y a los cuadros originales. En este archivo `ffprobe` comunicó rotación `90°` mientras OpenCV comunicó `CAP_PROP_ORIENTATION_META=270°`; usar esos números sin declarar convención de giro produciría la orientación equivocada. La comparación visual y de matrices, no sólo los metadatos, confirmó la transformación aplicada.

La [ruta R08 `rope_media.probe()` de Weaver `cc5fb57`](https://github.com/AlterMundi/harmonic-weaver/blob/cc5fb57df815a2657eb06cbaa94fa8ad64d6ad2f/src/harmonic_weaver/lab/research/rope_media.py) aceptó el MP4 sin giro y **rechazó** el rotado con «Rotated media requires explicit display-coordinate adapter». Eso es una regla deliberada: R08 ata anotaciones de soga a dimensiones y hash de un medio sin ambigüedad de visualización. El [worker R09 de pose](https://github.com/AlterMundi/harmonic-weaver/blob/cc5fb57df815a2657eb06cbaa94fa8ad64d6ad2f/src/harmonic_weaver/lab/perception_worker.py) contiene una rotación explícita `np.rot90` a partir de `frame.rotation`, pero **no se ejecutó PyAV aquí**; el fixture sólo comprobó que `np.rot90` del cuadro no rotado coincide con la vista auto de FFmpeg/OpenCV para una matriz de `90°`. No puede afirmarse aún igualdad real de cuadros PyAV↔OpenCV en el worker.

## Derivado con el giro incorporado, sólo para este fixture

Se generó además un **tercer MP4** decodificando la copia rotada con la autorrotación de FFmpeg y codificando otra vez sin pérdida de RGB con base de tiempo del fixture `1/10240`. Su SHA-256 es `6771bfaf45cd7b60ad9e50ba077579343c03f53900fe008f53b99687b8e21596`, distinto del original. Sus cuatro cuadros coincidieron **píxel por píxel** con los que OpenCV entrega al leer automáticamente el MP4 rotado; no quedó giro en los metadatos. Conservó exactamente los cuatro ticks `0,1024,2048,3072` y fue aceptado por `rope_media.probe()` como medio de `32×64` píxeles de visualización. Así se obtuvo un derivado apto para anotar la soga **en este archivo construido**, sin alterar el original ni desplazar su reloj.

No es una receta genérica validada para videos humanos: otros codecs, tasas variables, anamorfismo, giros, filtros o marcas de tiempo pueden cambiar orden, píxeles o PTS. En un material autorizado, la transformación y el par de hashes se registrarían como vínculo original→derivado; se comprobaría cada tramo usado, no se supondría equivalencia por el nombre del archivo. El comando del script fija `-video_track_timescale 10240` **porque ésa es la base de este fixture**, no como constante para las cámaras de Nico.

| Ruta | MP4 con matriz `90°` | Tiempo | Marco de imagen constatado |
|---|---|---|---|
| HarMoCAP PR #4, probe PTS | Acepta | PTS fuente intactos | El probe no examina orientación; OpenCV por defecto decodifica rotado en este entorno |
| Weaver R08, anotación 2D de soga | Rechaza | No crea anotaciones | Exige adaptar visualización antes de enlazar hash/dimensiones |
| Derivado sintético con giro incorporado → R08 | Acepta | Mismos cuatro ticks en el fixture | Píxeles mostrados iguales a OpenCV autorrotado, hash **nuevo** |
| Weaver R09, pose | Código contempla `frame.rotation` | PyAV conserva `frame.pts` en código | Runtime PyAV **no probado** con este archivo |

**Decisión para el estudio:** antes de combinar muñeca, soga, planos Laban y fase HIT en un video de baile o de Nico, fijar el sistema de coordenadas de visualización por archivo. Si se crea un derivado con giro incorporado para R08, conservar hash del original y del derivado, transformación exacta, dimensiones, orden de cuadros y mapeo PTS; verificar la identidad de píxeles entre la ruta de pose y la de anotación sobre cuadros representativos, incluidos principio, giro y fin. No basta quitar la metadata de rotación: eso cambia el sentido de lo que se ve sin mover sus píxeles. Una discrepancia de orientación debe invalidar la relación mano–soga hasta corregir el adaptador; no se compensa ajustando fase a posteriori.

La prueba se ejecutó dos veces con los mismos SHA del MP4 sintético rotado (`5f4cca467a1d66172d85092bb74d3b16f191560bb0f110e491b67222548a1442`) y del derivado orientado (`6771bfaf45cd7b60ad9e50ba077579343c03f53900fe008f53b99687b8e21596`); compilación Python y `git diff --check` quedaron limpios. Entorno: FFmpeg/ffprobe `6.1.1-3ubuntu5`, OpenCV `5.0.0`; código HarMoCAP `e0bdafc`, Weaver `cc5fb57`. Cambios de backend/versión requieren repetirla. La prueba no certifica exactitud de pose, sincronía óptica ni funcionamiento de Beacon.
